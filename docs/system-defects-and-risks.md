## SYS-001 代理删池与运行时清理缺少可靠补偿

- 发现日期：2026-09-08，Phase 5.0 静态盘点及 Terra 交叉审计。
- 状态：**已确认代码隐患，暂缓修复，不阻塞重构**。用户于 2026-09-08 明确要求先落档，主线继续重构。
- 证据基线：`805b3cc`；入口为 `scripts/proxy_pool.py` 的 `delete_pool`、`ensure_proxy_cores`、`_remove_mihomo_pool_config`、`_restore_mihomo_listener_config`。后续模块迁移以符号和 Git 历史定位，避免固定行号失效。

### 触发条件与影响

1. sing-box 管理的代理：`delete_pool` 先提交数据库软删、账号解绑和等待任务状态，再写配置并重启代理核心。如果配置写入或重启失败，数据库已经提交，运行时可能尚未清理完成；再次调用原删除入口会因代理已软删而报不存在，无法借此重试。
2. Mihomo 管理的代理：数据库写入失败时会尝试恢复配置，但恢复异常被忽略。数据库回滚不代表运行时已经恢复，缺少明确的失败记录和对应重试状态。
3. 影响仅在上述异常路径触发时成立。当前没有本次盘点中真实数据故障的复现证据，不将静态发现写成已发生事故。

### 当前恢复能力与局限

服务启动会再次尝试生成并重启 sing-box 配置，Mihomo 有现有 reconcile 入口；这些不等同于与特定删池操作绑定的可靠恢复机制。已删除代理不会继续走活动代理重检，补偿过程也没有持久操作状态。此记录不授权对真实数据库、代理配置或绑定执行修复操作。

### 与重构的边界

Phase 5 保留当前成功/失败行为，仍使用隔离 fixture 和故障注入检查迁移未引入新的不一致。允许上述已登记的既有缺陷继续存在；不得把它描述为已修复，也不得为满足原计划的理想补偿要求顺手新增状态、重试 API 或迁移真实数据。

后续单独安排修复时，再决定保留已提交删除并持久重试清理，或恢复删除前状态；至少验证配置清理失败、数据库提交失败、配置恢复失败和核心重启失败，检查账号、任务、数据库与配置的一致性及重复操作的幂等性。本次不选定、不实现修复方案。
