# 4004 FastMoss 选品决策 Skill V2：证据契约与旧链路收敛计划

> 状态：待实施，作为 V2 唯一实施依据
>
> 日期：2026-08-01
>
> 作用范围：仅 `codex/ui-beautification-4004`、仅 FastMoss「选品决策 / 解压玩具」预设
>
> 不影响：4002、4003、主页 SociaVault、Amazon / SellerSprite、FastMoss 其他四个官方预设
>
> 替代文档：`docs/fastmoss-lightweight-skill-repair-plan-2026-08-01.md`

## 1. 结论与目标

上一版轻量 Skill 修复了错年、无效调用和二次综合过短等工程问题，但没有显著提高卖家选品可用性。V2 不再以“调用更少、链路更短、回答更长”为目标，而是建立一套可验证的选品证据交付标准。

V2 的核心原则是：

> 固定证据口径、事实表和声明边界；不固定工具调用顺序、工具数量或最终业务结论。

具体目标：

- 模型继续自主选择 FastMoss 官方 MCP 工具、顺序和调用次数，不改成固定 Python 流程剧本。
- 后端按“能力证据契约”判断数据是否足够，而不是按是否调用某个固定工具判断完成。
- 原始 MCP 数据经过归一化后形成不可被最终模型删改的事实区块。
- 最终模型只负责解释、比较和建议，不能重写数字、混用口径或隐藏已返回的关键数据。
- 数据不完整时明确降级为初筛或快照，不能为了给结论而补猜。
- 保留当前 FastMoss MCP、工具权限、缓存、会话和 UI 基础设施，不回退 REST 或 mock。
- 分阶段收敛三类历史链路，先留可控回滚，再独立删除确认无调用的旧代码。

## 2. 本轮复盘依据

### 2.1 三版真实产物对比

| 版本 | 工具调用 | 工具耗时 | 最终输出 | 主要优点 | 主要问题 | 决策可用性 |
|---|---:|---:|---:|---|---|---:|
| 官方完整 Skill | 19 次 / 5 轮 | 7.681 秒 | 3,280 字 | 有 Top 10、商品链接和较多原始数据 | 8 次先查错 2025 年再返工；口径与结论仍有错误 | 约 4.5 / 10 |
| 首版本地轻量 Skill | 5 次 | 较低 | 首稿 1,661 字，综合后仅 267 字 | 调用相关性较高 | 二次综合把有效首稿压缩成追问尾巴 | 约 1.5 / 10 |
| 修复后本地轻量 Skill | 8 次 | 2.289 秒 | 2,029 字 | 无错年、无返工，链路效率明显改善 | 表格、链接和大量证据丢失；仍有口径混用和无依据结论 | 约 5 / 10 |

修复后版本相较官方版本将调用数减少约 58%，工具耗时减少约 70%，但用户可见的选品价值只从约 4.5 分提高到约 5 分。工程效率提高不等于业务质量达标。

### 2.2 已确认的可用性缺陷

- 以单日榜代替稳定的完整周或完整 7 日基线，容易受当天波动影响。
- MCP 已返回热销、新品、趋势和渠道数据，最终答案却没有保留 Top 10 表、商品链接和关键字段。
- 将直播 `46% GMV 占比` 与联盟 `52% 销量占比` 并列比较，混用了渠道与分母。
- 强新品证据集中在 `$23.87–27.92`，答案却无充分依据地建议优先 `$8–15`。
- 示例商品的商品卡占比分别达到 `54%` 和 `92%`，答案仍给出“只做商品卡不建议进入”的矛盾结论。
- 仅凭增长或单一工具结果判断“爆发、窗口开放、低竞争”，缺少趋势和领先指标共同验证。
- 旧官方版虽然数据更多，但调用剧本过长、先用错误年份查询、又把上游类目数据包装成目标类目结论。

因此，V2 必须同时保留当前精简链路的效率优势，以及官方产物中表格、链接和可审计数据的优点。

## 3. 范围与非目标

### 3.1 本次实施范围

- FastMoss `fm-product-scout` / 「选品决策」预设。
- 选品请求的范围确认、动态工具编排、证据归一化、确定性数据区块、声明校验、降级、缓存规范化和回归验收。
- 4004 的灰度、正式启用和旧链路收敛。

### 3.2 明确不做

- 不把工具顺序写成固定的 1 至 N 步执行器。
- 不要求每轮调用固定数量工具；工具数只作为成本和熔断指标，不作为质量通过条件。
- 不让官方长 Skill 原文再次直接控制完整对话。
- 不增加 REST、mock 或跨供应商工具回退。
- 不缓存整轮 LLM 最终答案。
- 不迁移或重写历史会话。
- 不在本轮改造 FastMoss 另外四个官方预设。
- 不因清理旧代码而重构共享的 SellerSprite、Amazon 或 SociaVault 支撑代码。

## 4. 当前链路盘点与处理结论

### 4.1 链路 A：FastMoss 官方完整 Skill

当前作用：

- `scripts/fastmoss_official_skill.py` 从固定官方版本加载 Skill。
- 其他 FastMoss 官方预设仍依赖官方加载器、官方工具定义和静态工具白名单。
- 旧版选品决策曾直接使用官方长 Skill 驱动多轮调用。

处理：

- 保留官方 Skill 加载器、固定版本、工具文档和工具白名单，它们仍是工具能力与权限边界依据。
- 选品决策在 V2 `enforce` 后不再把官方长 Skill 作为默认执行提示词。
- 官方选品链路在短期内只作为运维回滚基线，不允许请求内静默回退。
- 其他四个 FastMoss 预设继续使用现有官方链路，本次不动。
- 回滚观察期结束后，只删除选品决策专属的官方执行分支，不删除共享官方加载器。

### 4.2 链路 B：当前本地轻量 Skill V1

当前作用：

- `scripts/fastmoss_lightweight_skill.py` 加载本地轻量 Skill。
- `scripts/skills/fastmoss/BASE.md` 和 `scripts/skills/fastmoss/fm-product-scout.md` 定义当前本地提示词。
- `FASTMOSS_SKILL_SOURCE=local|official` 控制选品决策使用的提示词来源。
- 当前实现依靠两次模型综合和文本长度兜底，尚未形成真正的证据质量门槛。

处理：

- V2 实施期间冻结 V1，不继续在 V1 上叠加修补逻辑。
- `shadow` 和初始 `enforce` 阶段保留 V1，作为整个请求的运维回滚路径。
- V2 出错时不得在同一请求内自动切回 V1；应返回确定性事实区块、明确缺口或明确错误。
- V2 稳定观察期通过后，删除 V1 的选品路由、专属提示词和专属测试。
- `FASTMOSS_SKILL_SOURCE` 对选品决策标记为废弃；因其他预设仍需要官方加载器，不能以此为由删除共享能力。
- 回滚窗口内 `off` 仍尊重该配置：默认回到本地 V1；只有运维人员显式同时选择 `official` 时才回到官方完整选品 Skill。

本计划中的“回滚窗口”从第一次受控切换 `enforce` 开始，至少持续连续 7 个自然日。只有第 19、20 节全部通过、期间没有因质量问题回滚，并由项目负责人明确记录关闭决定后，窗口才算关闭。

### 4.3 链路 C：更早的固定意图、Playbook 与阶段编排

当前代码仍存在 FastMoss 旧阶段规划、必需工具组、深挖工具组、证据缺口和确定性规划相关符号，例如：

- `FASTMOSS_PRODUCT_REQUIRED_GROUPS`
- `FASTMOSS_PRODUCT_DEEP_DIVE_TOOLS`
- `fastmoss_workflow_phase`
- `fastmoss_analysis_evidence_gaps`
- 旧动态 planner / playbook / semantic report 分支

当前 `FASTMOSS_OFFICIAL_SKILL_ENABLED=1` 时，FastMoss 请求通常会直接进入 official-chain 分支，因此其中相当一部分旧 intent / planner 主路径已不可达；但应通过调用图确认，而不能仅凭运行观察直接删除。

处理：

- 不恢复旧版固定状态机，不让它重新决定工具的硬顺序或固定数量。
- 复用其中已经成熟且仍正确的“能力分组、语义事实、证据清单、冲突检测、声明验证”思想和解析代码。
- 将可复用能力移入 V2 明确模块后，旧 FastMoss 专属入口先标记 deprecated 并停止路由。
- 只有在 CodeGraph 证明无生产调用、对应测试已迁移、V2 稳定观察期通过后，才在独立清理提交中删除。
- 共享给 SellerSprite、Amazon 或通用聊天的代码即使名称相近也不得删除。

### 4.4 必须持续保留的基础设施

以下不是应被清理的“旧业务链路”：

- FastMoss 官方 MCP Bridge、运行时 `tools/list`、工具调用协议与异常恢复。
- 预设静态工具白名单，以及执行前的二次权限校验。
- FastMoss 文件缓存、持久化挂载和当前成功数据 TTL。
- API Key、MCP URL、会话存储、历史消息和前端工具调用展示。
- `fastmoss_evidence_renderer.py` 中可复用的事实归一化、证据 envelope / fact / fence 和冲突检测能力。
- 其他四个 FastMoss 预设使用的官方 Skill 能力。

## 5. 目标架构

V2 将目前被 `official_skill_chain` 一个布尔值混在一起的职责拆开：

1. **Instruction Source**：V2 本地选品 Skill，只描述任务目标、证据能力和写作边界。
2. **Tool Boundary**：沿用该预设固定的 FastMoss 官方工具白名单，schema 暴露和执行前各校验一次。
3. **Dynamic Orchestrator**：模型自主选工具；后端只返回当前证据覆盖和缺口，不编写固定工具剧本。
4. **Evidence Ledger**：把 MCP 结果归一化为带市场、实体、层级、周期、币种、指标和来源的事实。
5. **Contract Evaluator**：按事实能力评估 `sufficient / partial / insufficient / unavailable`，决定继续补证或停止。
6. **Deterministic Renderer**：生成口径卡和稳定数据表，最终模型没有删除或改写权限。
7. **Interpretation Model**：基于语义化证据做比较、解释、风险和下一步建议，不接收整包原始 JSON。
8. **Claim Validator**：校验高风险声明及数字引用；失败则定向修订、删除声明或降低报告等级。

建议新增独立模块 `scripts/fastmoss_product_scout_v2.py` 承载契约、覆盖评估和声明规则；扩展现有 `scripts/fastmoss_evidence_renderer.py` 输出稳定事实区块，避免复制一套解析器。

最终解释必须显式使用现有 `FASTMOSS_REPORT_MODEL`，不能因为上游路由仍被标记为 `direct` 而意外继承 Flash / 快速模型。确定性校验始终为必需层；`FASTMOSS_LLM_VERIFIER_ENABLED` 只可作为第二层语义审阅，不能覆盖确定性校验失败，也不能成为 V2 正常出报告的单点依赖。

## 6. ProductScoutEvidenceContract

契约约束“需要取得什么事实”，不约束“必须调用哪个工具”。建议内部结构如下：

```text
scope
  market: value + source
  category: L1/L2/L3 id + name + match status
  requested_period
  actual_periods
  currency
  sort
  source=FastMoss

market_evidence
  scale
  growth
  channel_structure
  competition_or_concentration
  grain
  status

  actual_period
  sort
  returned_count
  rows
  rejected_rows
  status

new_ranking
  listing_window
  sort
  returned_count
  valid_rows
  rejected_rows
  status

candidate_validations[]
  product_identity
  selection_reason
  sales_trend
  creator_video_live_leading_signals
```

每一条归一化事实必须保留：

- `fact_id`、原始实体 ID 和可用链接。
- `source_ref`：工具、调用、结果位置，不能包含密钥或完整敏感结果。
- 实际市场、类目 ID、类目层级、周期、币种。
- 指标名、数值、单位、分母和排序字段。
- `data_state=verified|partial|empty|error|not_attempted`。
- 缓存命中、缓存 age 和数据时间。

## 7. 范围、日期与默认值

### 7.1 市场来源

市场只能来自：

1. 用户本轮明确指定。
2. 当前会话中已经确认且仍适用的市场。
3. 页面明确配置的应用默认值。

如果使用应用默认美国站，口径卡必须显示“美国站；来源：页面默认”，不得写成用户主动选择。无可靠来源或用户表达多市场歧义时，先询问市场，付费工具调用数为零。

当前应用执行层会对缺失区域静默补 `US`。V2 必须把“市场选择”和“执行参数补默认”分开，执行层默认不得反向伪装为用户意图。

### 7.2 类目层级

- 保存 L1、L2、L3 的 ID、名称和匹配状态。
- 类目匹配接近时展示前两个候选并请求确认，确认前停止后续付费查询。
- 上游 L1 / L2 数据只能标记为“上游代理参考”，不得呈现为目标 L3 的规模、增长或集中度。
- 规模、增长、竞争和渠道结论必须与实际层级绑定。

### 7.3 稳定周期

- 发现基线优先使用最新完整 7 天或 FastMoss 支持的最近完整周。
- 单日榜只用于识别短期异常和爆点，并明确标注“单日信号”，不能替代稳定基线。
- 新品默认查看近 14 天上新；有效样本不足时最多扩展一次到 30 天并披露。
- 候选验证使用实际可得的 28 / 30 天趋势，并配合 7 日或周度增长。
- System Prompt 可注入运行时日期，但所有输出使用接口实际返回周期；禁止根据当前日期猜造数据日期。

## 8. 动态工具编排

### 8.1 运行规则

- 首轮根据范围和契约缺口选择真实 FastMoss 工具。
- 每批结果归一化后由 `ContractEvaluator` 返回已覆盖能力、缺失能力、冲突和不可用能力。
- 模型只看到“还缺什么事实”，自主选择下一工具；后端不指定唯一工具名称和硬顺序。
- 达到 `sufficient`、预算 / 轮次上限或能力确认不可用时停止。
- 同一轮出现完全相同的语义调用签名时阻止重复执行，并把已有事实反馈给模型。
- 工具调用总数只受安全熔断限制；“调用 2 个”或“调用 19 个”本身都不代表成功或失败。

### 8.2 选品能力最低覆盖

- 范围：市场、币种、目标类目与层级、实际周期。
- 市场背景：同层级规模、增长、竞争 / 集中度；若只能取得上游数据必须降级标注。
- 热销格局：稳定周期热销榜及其有效记录。
- 新品格局：合法上新窗口内的新品榜和去噪结果。
- 候选验证：对实际推荐的 1 至 3 个商品获取销售趋势，以及渠道、达人、视频或直播中的至少一种近期领先信号。
- 证据缺口：未取得、为空、冲突、粒度不匹配或工具失败都必须进入结果。

### 8.3 结果去噪

以下记录进入“剔除 / 待确认”区，不得直接进入机会结论：

- 屏幕展示、测试链接或无法确认的占位商品。
- 明显重复铺货链接。
- 商品身份或类目冲突。
- 极端异常价格且无法确认实体。
- 数据期、市场或币种与当前范围不一致。

去噪不能静默：必须保留返回总数、展示数、剔除数和剔除原因。

## 9. 确定性输出契约

最终回答由“确定性事实区块 + 模型解释区块”组成。模型解释可以更短或更长，但不得删除、重算或重写事实区块。

### 9.1 必须区块

1. **口径卡**
   - 市场及来源。
   - 类目路径、实际层级和 ID。
   - 热销、新品、候选验证各自的实际周期和排序。
   - 币种、数据源、实时 / 缓存及缓存 age。

2. **市场与类目表**
   - 规模、增长、渠道、竞争 / 集中度。
   - 每项标出实际粒度；上游代理数据单独展示。

3. **热销榜**
   - 返回 10 条时展示 Top 10；少于 10 条时展示全部并标记实际数量。
   - 至少包含商品 / 链接、ID、价格、店铺、周期销量、周期 GMV、增速、累计指标、佣金率和上架日中所有实际可得字段。

4. **新品榜**
   - 去噪后目标至少 3 条；返回 10 条有效数据时展示 Top 10。
   - 包含商品 / 链接、ID、价格、上架日、早期销量 / GMV、累计指标、店铺、跨境 / 托管和佣金中所有实际可得字段。

5. **候选验证表**
   - 对 1 至 3 个候选并列展示选择原因、趋势、销量 / GMV、达人 / 视频 / 直播领先信号、渠道占比、集中度、阶段、证据状态和淘汰 / 保留原因。
   - 只有一个有效候选时明确写“个案观察”，不能包装成价格带或赛道规律。
   - 可使用“优先验证 / 观察 / 排除”标签，但不生成缺乏客观权重的伪精确综合分。

6. **结论、风险与下一步**
   - 仅使用通过声明校验的结论。
   - 给出下一步验证对象、原因和缺失数据，不自动升级为备货建议。

7. **数据缺口与剔除项**
   - 列出空数据、失败工具、口径冲突、剔除实体和导致的结论限制。

### 9.2 渲染规则

- 数字由归一化事实直接渲染，不让模型手工抄写或重新计算。
- 商品链接由事实层生成，模型不能编造。
- 佣金率为 `0` 时写“接口值 0 / 待确认”，不能直接解释成免佣。
- 不同数据集周期分别写明，不能用一个全局日期覆盖。
- 冲突数据并列展示，不能由模型擅自挑一个。
- 最终综合输入语义化 dossier，不输入整包原始 JSON。
- 第一稿只能作为表达参考，不能成为事实来源。

## 10. 声明边界与强制校验

### 10.1 高风险声明最低证据

| 声明 | 最低证据 | 证据不足时允许的表达 |
|---|---|---|
| 类目值得进入 | 同层级规模、增长、竞争 / 集中度 | “值得继续初筛” |
| 最佳价格带 | 至少 3 个独立有效样本，同时比较销量、GMV 和趋势 | “当前样本集中在……” |
| 利润 / 毛利更好 | 成本、平台费用及其他毛利证据 | 禁止输出利润判断 |
| 低竞争 | 参与者数量加贡献集中度 | “竞争证据不足” |
| 直播 / 视频 / 商品卡驱动 | 同口径直接渠道分布 | “样本渠道结构为……” |
| 成长 / 爆发 / 窗口开放 | 销售趋势加近期达人、视频或直播领先信号 | “销售增长样本” |
| 唯一 / 最好 / 只有它 | 对全部符合条件候选完成同口径比较 | “在已分析样本中” |
| 新品赛道已验证 | 至少 3 个去噪新品，且不能全部来自同一店铺 | “新品样本不足” |
| 市场无垄断 | 目标类目同层级集中度 | 禁止用上游层级替代 |
| 自然流量 | 广告或渠道分布的直接证据 | 禁止由“未调用广告工具”推断 |

### 10.2 数值与逻辑校验

- 数值、单位、币种、周期、实体和分母必须绑定 `fact_id`。
- 百分比只允许显示舍入，误差不得超过 0.1 个百分点。
- 明确区分 GMV 占比与销量占比，以及商品卡、联盟、直播和视频。
- 不得跨 L1 / L2 / L3 复用规模或集中度。
- “日新增仍为正”不等于“增速继续上升”，必须比较连续时间点。
- “视频列表为零”不能推出“全部靠直播”，仍需直接渠道数据。
- 累计达人数量不等于近期达人增量。
- 每个行动性推荐至少绑定两条证据；高风险声明必须全部通过。
- 校验失败先进行一次定向修订；仍失败则删除该声明并降低覆盖等级。

### 10.3 质量门槛替换

删除“回答长度达到某个字符数即合格”的逻辑。新的质量门槛必须检查：

- 证据契约覆盖等级。
- 必须区块是否存在。
- 返回数据的行数与字段保留率。
- 数字引用与原始事实一致性。
- 市场、币种、层级和周期一致性。
- 高风险声明是否有证据。
- 失败和空数据是否正确降级。

## 11. 覆盖等级与允许结论

### A：决策就绪

同时满足：

- 口径卡完整。
- 有同层级市场规模 / 增长及竞争证据。
- 热销有效记录不少于 5 条。
- 新品去噪有效记录不少于 3 条。
- 至少 2 个候选完成趋势和领先指标验证。
- 所有高风险声明通过。

允许给出进入判断、优先形态和验证顺序；没有成本和费用数据时仍禁止利润或备货量结论。

### B：初筛就绪

最低要求是：口径卡完整、热销有效记录不少于 3 条、新品去噪有效记录不少于 1 条，并取得规模、增长、竞争 / 集中度中的至少一类同层级市场证据；候选领先指标可以不完整。

只允许给出值得继续研究的方向、候选排序和待验证项；不得输出确定窗口、最佳价格带或备货建议。

### C：数据快照

至少存在一条可信业务事实，但未达到 B 的最低要求，例如只有热销或新品中的一类、记录数不足，或目标类目市场证据无法取得。只展示已有数据和局限，不做类目机会判断。

### D：不可用

无有效业务数据，或鉴权、余额、MCP / 协议故障。明确返回错误，不生成市场结论，不回退 REST、mock、V1 或旧官方 Skill。

### 11.1 运行状态到覆盖等级的唯一映射

- 单项事实的 `verified / partial / empty / error / not_attempted` 先汇总为契约运行状态。
- `sufficient`：只有满足 A 的全部量化门槛时成立，对应 A。
- `partial`：达到 B 的明确最低门槛时对应 B；未达到 B 但至少有一条可信业务事实时对应 C。
- `insufficient`：仍有可信事实时对应 C；没有可信业务事实时对应 D。
- `unavailable`：鉴权、余额、MCP / 协议故障或全部事实不可用，对应 D。
- 高风险声明验证失败时先删除该声明；只要发生过高风险声明失败，本轮最高只能为 B。
- 市场、币种、实体、类目层级或关键数字一致性验证失败时，本轮最高只能为 C。
- 全部可信事实丢失或无法安全渲染时为 D。

## 12. 缓存与 TTL

### 12.1 保持不变的部分

- 继续使用 FastMoss Bridge 的文件缓存和持久化挂载。
- 成功数据 TTL 保持 `86,400` 秒（24 小时），不是主页 `api_cache.sqlite` 的 7 天 TTL。
- 不缓存整轮 LLM 答案。
- 容器替换后缓存仍应存在。

### 12.2 当前未命中的根因与修复

当前缓存键按 provider / scope / endpoint / 原始 request 精确生成。模型两轮即使语义相同，只要省略默认值、显式填写默认值、类型或空值不同，就会得到不同键；模型选择不同候选深挖时也不是相同调用。

已观察到的直接例子是：同一个类目搜索，一轮发送 `{query:["解压玩具"]}`，另一轮多发送 `top_k:5`；MCP 最终都按 `top_k=5` 执行，但缓存键在补默认值前生成，因此两次都 miss。另一次回归将完整周改为单日、将 `category_id` 改为 `category_l3_id` 并改变上新窗口，这些本来就是不同请求，不应误判为缓存故障或强行合并。

V2 必须先按官方 schema 形成“有效请求”，再计算缓存键：

```text
provider
+ credential_or_mcp_url_scope
+ endpoint
+ tool_schema_version
+ normalized_effective_request
```

只规范化官方确认等价的差异：

- 对象键排序。
- 统一地区、语言、空值和数字类型。
- 省略的官方默认值与显式相同默认值统一。
- 只统一官方确认等价的字段别名。

以下字段必须保留，绝不能错误合并：

- 市场、类目 ID、商品 ID。
- `day` / `week` 等统计粒度。
- 实际起止日期、上新窗口。
- 排序、页码和业务筛选。
- `orderby` 等有语义顺序的数组。

### 12.3 旧缓存处理

- 不清空现有缓存文件，不改持久化目录。
- 新键使用版本化 namespace，避免与语义不明确的旧键错误串用。
- `shadow` 期间利用同一次真实调用或旧缓存命中结果写入规范化新键，不增加付费 MCP 调用。
- 不做无条件旧键双读；只有能从旧条目的请求元数据证明与新有效请求完全等价时才允许复用。
- 可复用的旧条目必须同时具备相同 provider scope、endpoint、兼容的 tool schema 版本、可重建且完全相同的 normalized effective request，以及成功 / 正常空集合状态；缺一项即不复用。
- 写入新 namespace 时继承旧条目的原始 `fetched_at` 与 `expires_at`，只保留剩余 TTL，绝不重新开始 24 小时计时。
- 不能证明等价的旧条目让其按原 24 小时 TTL 自然过期。
- 鉴权、余额、协议、超时、进程错误和异常空响应不缓存。
- 经 schema 确认的正常空集合可使用 5 至 10 分钟短 TTL，并标记 `data_state=empty`。

### 12.4 缓存诊断与验收口径

结构化日志记录 `hit/miss`、`miss_reason`、endpoint、规范化键前缀、TTL、age 和 scope 版本，不记录密钥、完整参数或结果。

“相同问题”不等于所有工具调用都相同。验收定义为：同一已确认市场、类目、日期、排序和筛选下，第二轮实际重复出现的基础调用必须 100% 命中；第二轮新选择的候选深挖不计为漏命中。

## 13. 故障、空数据与综合失败

| 情况 | 处理 |
|---|---|
| 市场缺失 | 先确认市场，零付费调用 |
| 类目匹配接近 | 展示前两个候选并确认，确认前停止 |
| 热销为空 | 合法调整一次稳定周期；仍为空则降为 C |
| 新品为空或全是噪声 | 上新窗口最多扩展一次；仍不足则 B / C |
| 候选趋势缺失 | 保留候选，禁止阶段和窗口结论 |
| 渠道数据缺失 | 禁止直播 / 视频 / 商品卡归因 |
| 部分工具失败 | 其他区块继续，失败区块标记 unavailable |
| 达到轮次或成本上限 | 按当前覆盖等级输出，不能为了凑结论升级 |
| 数据冲突 | 并列展示口径与冲突，不能自动覆盖 |
| 最终综合超时或退化 | 返回确定性事实表、已通过校验的保守摘要和失败说明 |
| MCP、鉴权或余额错误 | D 级明确错误，不回退任何旧数据源或旧链路 |

过期缓存只有在用户明确同意后才能展示，并必须标记 cache age、原周期和“非实时”；MCP 故障时不得自动把过期缓存伪装成实时结果。

## 15. 模式、上线与回滚

### 15.1 模式定义

- `off`
  - 继续使用当前 V1 用户可见链路，并在回滚窗口内尊重 `FASTMOSS_SKILL_SOURCE`；默认 `local`，显式 `official` 才使用官方完整版本。
  - 仅作为实施期和短期观察期的运维回滚。
- `shadow`
  - V2 动态编排器负责本轮唯一一次真实工具规划和 MCP 调用，以便真实验证编排；不得同时运行 V1 工具规划。
  - 用户仍由当前 V1 输出 composer 基于这同一批 V2 工具结果生成可见回答；V2 evidence contract、覆盖等级、事实区块和声明诊断只记入 shadow 诊断。
  - 因此 shadow 不重复执行付费工具，也不额外产生一轮必需 LLM 调用；它保证输出形态不切换，但工具选择行为已经进入受控验证。
  - shadow 仅在 4004 受控测试窗口使用；若 V2 规划失败则明确报错并记录，不在请求内启动 V1 planner。
- `enforce`
  - V2 事实区块和通过验证的解释成为用户可见结果。
  - 请求内失败按第 13 节降级，不静默切换 V1。

### 15.2 上线顺序

1. 在 4004 本地实现契约、renderer、声明校验、缓存规范化和 fixtures。
2. 运行自动测试、脱敏 golden 回归和隔离故障注入；未通过时不得部署 shadow。
3. 以 `shadow` 部署 4004，在受控请求中由 V2 执行唯一真实 MCP 链路，验证工具规划、缓存命中、空数据和实际证据覆盖。
4. 对 shadow 失败样本修正规则；第 19.1 的硬失败项必须为零，才允许首次切换 `enforce` canary。
5. 以 `enforce` 在 4004 执行受控 canary，立即验证最终页面、真实 MCP、缓存、综合超时和可安全模拟的进程异常；任一硬门槛失败立即切 `off`。
6. canary 全部通过后才将 4004 保持在 `enforce`，并连续观察 7 个自然日；期间不得出现 P0 / P1 事实错误。
7. 第 19、20 节全部达标并由项目负责人明确确认关闭回滚窗口后，单独执行旧链路清理，不把清理与功能上线放在同一提交。

### 15.3 运维回滚

- 将 `FASTMOSS_PRODUCT_SCOUT_V2_MODE` 设为 `off` 并只重启 / 重新部署 4004。
- 回滚不改数据库、不迁移会话、不清缓存、不触碰 4002 / 4003。
- 每次回滚记录触发样本、覆盖等级、失败声明和实际工具结果诊断。
- 不允许通过请求内自动回退掩盖 V2 故障。

## 18. 真实回归集

## 19. 验收标准

### 19.1 硬失败项

出现任一项即不得上线：

- 错年、未来周期或接口未返回的日期。
- 静默市场默认，或将页面默认写成用户选择。
- 将 L1 / L2 数据呈现为目标 L3 数据。
- 关键数字、单位、币种、分母或实体不匹配。
- 混用 GMV 占比与销量占比，或混用商品卡、联盟、直播、视频。
- 无证据的利润、低竞争、最佳、唯一、爆发或窗口开放声明。
- MCP 返回 Top 10 有效数据但最终隐藏关键行。
- 跨 provider 工具、REST / mock 回退或请求内旧链路静默回退。

### 19.2 自动阈值

| 维度 | 门槛 |
|---|---|
| 市场 / 类目 / 周期 | 100% 正确，零静默默认 |
| 必需字段展示率 | 来源有值的字段 100% 保留 |
| 关键数值可追溯率 | 100% 绑定事实来源 |
| 热销覆盖 | 有 10 条展示 10 条；不足时展示全部 |
| 新品覆盖 | 去噪后至少 3 条，否则正确降级 |
| 候选验证 | 行动结论至少 2 个候选；仅一个时标记个案 |
| 高风险声明 | 无证据声明数为 0 |
| 粒度一致性 | L1 / L2 / L3 错用数为 0 |
| 重复调用 | 同语义签名重复执行数为 0 |
| 缓存 | 第二轮重复基础调用命中率 100%，错误串命中 0 |
| 最终综合 | 确定性区块完整率 100% |
| 工具次数 | 仅要求不超过熔断并无语义重复；不设质量达标数量 |

### 19.3 卖家可用性评分

每项 1 至 5 分：

1. 数据口径是否一眼可见。
2. 热销和新品能否直接横向比较。
3. 推荐能否追溯到具体数据。
4. 风险和缺口能否阻止错误下单。
5. 看完是否知道下一步验证哪个商品、为什么。

真实回归由两名具备选品经验的审阅者独立评分：

- 两人平均分均不得低于 `4.2 / 5`。
- 任一单项不得低于 `4 / 5`。
- 不得存在高风险无证据声明。
- 回答变长、工具变多或措辞更专业不能替代上述门槛。

另使用 10 分技术业务联合评分：范围正确 2 分、数据完整 2 分、数值可追溯 2 分、比较与决策支持 2 分、行动下一步 1 分、局限 1 分；必须达到 8 分且无硬失败项。
