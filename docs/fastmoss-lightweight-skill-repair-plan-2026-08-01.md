# 4004 FastMoss 轻量 Skill 修复计划

> **状态：V1 复盘文档，已停止作为实施依据。**

## 1. 目标

把当前 FastMoss 预设链路从“逐字加载官方长 Skill”调整为：

- FastMoss MCP 继续作为唯一实时数据来源。
- 官方 Skill、Playbook 和工具文档作为业务依据与工具边界依据。
- 4004 使用自有轻量 Skill 完成任务理解、证据目标和回答质量控制。
- 模型自主决定工具调用顺序，不引入固定步骤的 Python 工作流。
- 后端只执行日期、权限、重复调用、超时和数据真实性等必要约束。
- 工具调用完成后能够真正消化证据，避免“调用 19 个工具、最终回答却很短”。

## 2. 官方资料结论

### 2.1 CLI、MCP 和 Skill 的职责不同

- FastMoss CLI 负责安装、鉴权、`tools` 工具发现和直接 `call`。
- MCP 提供实时 TikTok Shop 数据和可调用工具。
- Skill 是给模型使用的业务判断与回答指导，不是确定性工作流执行器。
- 4004 已有 MCP 调用链，不需要为了使用官方 Skill 再套一层 CLI 进程。

官方资料：

- [安装 FastMoss CLI](https://developers.fastmoss.com/zh/docs/cli/install.html)
- [配置 FastMoss MCP 与安装 Skills](https://developers.fastmoss.com/zh/docs/mcp/setup.html)
- [FastMoss 官方 Skill 仓库](https://github.com/FastMoss/fastmoss-skills)

### 2.2 官方 Skill 值得保留的内容

- MCP 不可用、未鉴权或调用失败时不得编造实时数据。
- 每个请求优先匹配一个主 workflow。
- 对象名称或链接先解析真实 ID，再调用详情、趋势、列表和分析工具。
- 类目任务先使用 `search_category_by_words` 解析类目。
- 同一比较必须保持市场和时间口径一致。
- 空结果表示“未获取到数据”，不能直接解释成“市场没有活动”。
- 数据结论应标明 FastMoss 来源、筛选条件、排序和实际周期。
- 商品阶段判断优先看达人、视频增量等领先指标，再使用 GMV 验证。
- 视频策略必须来自真实视频、商品和销售证据，不能凭空生成卖点。

官方入口：

- [SKILL.md](https://github.com/FastMoss/fastmoss-skills/blob/main/SKILL.md)
- [PRINCIPLES.md](https://github.com/FastMoss/fastmoss-skills/blob/main/references/PRINCIPLES.md)
- [fm-product-scout.md](https://github.com/FastMoss/fastmoss-skills/blob/main/references/fm-product-scout.md)

### 2.3 不适合直接作为 4004 运行时提示词的内容

- 官方原则主动强调 `Less is more`。
- 选品 Scenario A 只要求排行表、3–5 个总结点和少量追问。
- 选品 Scenario B 明确限制为不超过 200 words 的正文加数据表。
- 固定三层结构会让不同问题得到相似的模板化答案。
- 全局 MossCreator、Oumomo 软推广会污染不相关的选品回答。
- 官方偏好记忆机制与 4004 当前请求级预设、会话存储能力不一致。
- 官方仓库与官网 Playbook 对输出字段、workflow 数量和部分工具可用性的描述存在不一致。
- 官方 Skill 只写“最近 7 天/30 天”，没有提供当前日期、时区和最近完整周期锚点。

因此官方材料应作为业务依据和更新对照，不应继续整包逐字注入模型。

## 3. 当前 4004 根因

### 3.1 日期上下文被丢弃

`fastmoss_official_skill_system_instruction` 收到了上海当前日期，却主动删除该参数并只返回官方原文。

同时，`apply_fastmoss_business_defaults` 只在旧 `playbook` 路由执行；官方 Skill 路由的 `playbook=None`，因此最近完整周期默认值没有进入这条链路。这会允许模型在 2026 年请求中生成 `2025-W25` 等过期参数。

### 3.2 官方路由直接返回采集模型草稿

- `fastmoss_official_skill_route` 使用 `task_depth="direct"`。
- `complete_fastmoss_answer` 对 `official_skill_chain` 直接返回原始 draft。
- 官方链路绕过现有最终报告综合能力。

因此调用次数和回答完整度没有关系：即使收集了大量证据，模型也可以按官方极简规则立即结束。

### 3.3 调用上限和去重不足

- 官方链路默认允许 24 轮工具调用。
- 当前去重只比较“工具名 + 完整参数 JSON”。
- 同一个业务查询只要换一个周次、分页或参数格式，就会被当作新调用。

最新会话中至少出现了同一批核心工具先查询 `2025-W25`、随后再查询 `2026-W30` 的重复；部分早期商品深挖也没有进入最终结论。

### 3.4 工具权限边界本身可继续使用

现有链路已经具备以下可靠边界：

- 预设静态工具白名单。
- 白名单与运行时 MCP 目录求交集。
- 工具执行前再次拒绝未暴露工具。
- 商品、类目等 ID 的来源校验。
- FastMoss、SellerSprite、SociaVault 工具域隔离。

本次修复不推翻这些边界。

## 4. 目标架构

```text
用户问题 + 当前预设
        │
        ▼
4004 轻量 Skill
（目标、证据、判断方法、完成标准）
        │
        ├── System runtime envelope
        │   （日期、时区、数据真实性）
        │
        ▼
仅暴露该预设允许的 FastMoss MCP 工具
        │
        ▼
模型自主选择并调用工具
        │
        ├── 后端必要保护
        │   白名单 / 日期 / 去重 / 超时 / 熔断
        │
        ▼
tools-off 最终综合
（自由写作，但必须消化有效证据）
        │
        ▼
最终回答
```

设计原则：

- 业务分析由模型和 Skill 完成。
- 后端不判断“市场好不好”，也不拼装固定业务结论。
- 后端只保护不可违反的运行时边界。
- 不以“必须调用 N 个工具”作为成功标准。
- 不以固定字数作为回答质量标准。

## 5. 硬约束与软指导

### 5.1 后端硬约束

仅保留以下不可违反的约束：

1. 实时数据只能来自 FastMoss MCP 返回结果。
2. 只能暴露并调用当前预设白名单内的工具。
3. 用户明确指定的历史日期优先于默认日期。
4. 相对时间不得被解释为明显过期或未来周期。
5. 空结果、余额不足、鉴权失败和 MCP 故障必须如实返回。
6. 相同工具、相同对象、相同统计口径的重复调用应被阻止。
7. 工具循环必须有超时和最大轮次熔断。

### 5.2 Skill 软指导

以下只作为模型判断依据，不写成程序状态机：

- 建议使用哪些核心工具形成基础证据。
- 什么情况下值得继续深挖。
- 哪些信号足以支持阶段或机会判断。
- 回答应覆盖哪些决策信息。
- 哪些信息不足时应主动说明限制。
- 什么时候已经足够回答，应停止继续调用工具。

## 6. 运行时日期设计

### 6.1 最小 System Prompt

每次 FastMoss 预设请求追加以下运行时上下文：

```text
当前日期：{YYYY-MM-DD}
时区：Asia/Shanghai
“当前、最近、近 7 天、近 30 天”等相对时间以此日期解析。
用户明确指定历史时间时，以用户指定时间为准。
不得查询未来周期；最终回答必须标明工具实际返回的数据周期。
```

不向 System Prompt 添加固定调用顺序、固定工具数量或固定回答模板。

### 6.2 窄范围参数保护

System Prompt 是第一层。执行前只增加一层窄范围校验：

- 用户没有指定绝对日期，模型却生成明显过期的年周参数时，修正为工具支持的最近完整周期。
- 模型生成未来周期时拒绝或修正，并记录结构化诊断日志。
- 用户明确要求历史周期时不得改写。
- 最终展示以工具响应中的实际时间范围为准。
- 只处理确实带日期/周期参数的 FastMoss 工具，不实现通用自然语言日期状态机。

## 7. 自有轻量 Skill

### 7.1 文件组织建议

```text
scripts/
  fastmoss_official_skill.py        # 官方来源下载、固定版本、完整性校验、更新对照
  fastmoss_skill.py                 # 4004 轻量 Skill 加载与选择
  skills/fastmoss/
    BASE.md                         # 共享真实性、日期和回答质量原则
    fm-product-scout.md
    fm-creator-outreach.md
    fm-competitor-batch.md
    fm-store-diagnosis.md
    fm-video-brief.md
```

官方固定提交和 SHA 校验继续保留，便于审计上游变化；但运行时默认读取本地轻量 Skill，而不是将官方四个 Markdown 文件整包拼接。

建议增加单一回滚配置：

```text
FASTMOSS_SKILL_SOURCE=local|official
```

4004 默认 `local`；出现异常时可以回到当前官方提示词，不影响 MCP 和缓存。

### 7.2 第一阶段：选品决策

先只重写 `fm-product-scout`，确认效果后再迁移其余四个。

轻量 Skill 不规定固定步骤，只定义以下任务目标：

- 判断用户属于泛方向发现，还是具体商品/类目验证。
- 市场缺失且确实无法推断时，只询问一个必要问题。
- 给出明确的进入判断或最值得继续研究的方向。
- 使用排行、市场或候选样本支撑结论。
- 涉及商品阶段时，必须有达人/视频增长等领先指标；GMV 只作为滞后验证。
- 至少说明关键驱动、主要风险和证据缺口。
- 给出一个能够直接继续执行的下一步。
- 已调用的深挖工具如果影响判断，应反映在最终回答中。
- 不输出与当前预设无关的产品推广。

官方 Scenario A 的核心工具组合仅作为推荐：

- `market_category_analysis`
- `market_category_ranking`
- `product_rank_new_listed`
- `product_rank_top_selling`

只有在需要判断具体商品阶段、入场窗口或解释异常时，再考虑：

- `product_overview`
- `product_creator_analysis`
- `product_video_list`
- `product_sales_trend`
- `product_investment`

不要求全部调用，也不固定调用顺序。

### 7.3 输出完整性目标

不设固定字数和固定标题，只要求在适用时覆盖：

- 用户问题的直接结论。
- 支撑判断的核心数据或样本。
- 数据中最重要的结构性驱动。
- 代表性机会或商品的进一步解释。
- 风险、冲突或数据缺口。
- 可执行的下一步。

回答可以简洁，但不能遗漏影响用户决策的有效证据。

## 8. 工具调用控制

### 8.1 模型继续拥有调用自主权

- 不做固定 A1/A2/A3 状态机。
- 不要求先后顺序，除非工具本身存在 ID 依赖。
- 模型判断证据足够后即可结束。
- 模型可以在空结果、错误或证据冲突时改用其他工具或时间窗口。

### 8.2 轻量语义去重

构造只用于重复检测的规范化签名：

- 工具名。
- 市场。
- 主要对象 ID 或类目 ID。
- 统计周期。
- 关键筛选条件。
- 分页信息。

只阻止相同业务范围的重复调用。以下情况仍允许调用：

- 合法的下一页。
- 用户明确要求另一个时间窗口。
- 上一次为空或失败，且本次确实修改了查询条件。
- 为验证冲突证据而使用不同工具。

### 8.3 最大轮次是熔断，不是目标

- `fm-product-scout` 第一版建议最大 12 轮。
- 不断言必须达到或接近 12 轮。
- 后续四个 Skill 的上限根据真实回归决定，不直接复制 24 轮。
- 达到上限时使用已经获得的证据完成回答，并明确未完成的部分。

正常泛选品任务预计从当前 19 次下降到约 6–12 次，但最终以证据充分性为准。

## 9. tools-off 最终综合

### 9.1 触发条件

本轮至少成功获得一条 FastMoss 数据证据，并且采集模型准备输出最终回答时：

1. 禁用所有工具。
2. 保留用户原始问题、选中的轻量 Skill 和当前有效证据。
3. 再执行一次最终综合。
4. 要求只使用现有证据，不再请求或描述新的工具调用。

### 9.2 不使用程序化报告模板

- 不使用确定性 Python 模板拼接最终报告。
- 不要求固定章节数量。
- 不把所有工具结果机械展开。
- 不因为工具调用多就强制写长文。
- 只要求消化与用户决策相关的主要证据。

### 9.3 高可用回退

- 最终综合成功：返回综合后的回答。
- 最终综合超时或模型失败：返回采集模型原始 draft，并附真实错误诊断日志。
- 不因第二次模型调用失败而丢失已经获得的有效结果。

该设计会增加一次 LLM 调用，但减少重复工具调用和无效上下文后，整体延迟与成本需要通过真实回归评估。

## 10. 其余四个 workflow 的迁移边界

选品通过后，按相同方式逐个迁移：

### 10.1 达人建联

- 目标：达人发现、匹配、评估和建联文案。
- 证据重点：真实带货表现、活跃度、品类匹配、受众和近期趋势。
- 不自动扩展成商品选品或完整店铺诊断。

### 10.2 竞品批量对比

- 目标：多商品、多店铺或多达人的横向比较，以及爆发归因。
- 证据重点：统一市场、统一时窗、渠道结构、达人结构、内容和价格差异。
- 不对每个对象机械生成一份长 dossier。

### 10.3 店铺诊断

- 目标：单店商品、渠道、达人、视频、直播、广告和集中度风险诊断。
- 证据重点：规模变化、结构变化、依赖度和异常。
- 多店横向比较交给竞品 workflow。

### 10.4 视频策略

- 目标：基于真实视频表现完成内容拆解、Hook、卖点和拍摄 brief。
- 证据重点：视频表现、商品信息、自然/广告信号和可复用结构。
- 不根据商品名称凭空编造脚本依据。

## 11. 缓存、TTL 和 MCP 保持不变

- API Key 环境变量和密钥传递方式。

- 缓存命中、失败和空数据的基本语义。

语义去重只控制本轮是否再次向模型执行相同工具，不改变持久缓存策略。

## 13. 自动测试

### 13.1 Prompt 和 Skill

- System Prompt 包含当前上海日期和时区。
- 用户显式历史周期仍保留。
- 本地 Skill 不包含无关 MossCreator/Oumomo 推广。
- 本地 Skill 不包含固定 200 words 限制和伪用户记忆规则。
- 每个 preset 只加载自己的 workflow。

### 13.2 工具边界

- 暴露工具必须同时存在于 preset 白名单和运行时 MCP 目录。
- 调用前再次拒绝未暴露工具。
- 不允许 SellerSprite、SociaVault 工具混入 FastMoss。
- 每个本地 Skill 引用的工具必须存在；排除官方工具时记录明确理由。

### 13.3 日期

- 当前相对时间使用最近完整周期。
- 年末、年初和 ISO week 切换正确。
- 用户明确的历史周期不被改写。
- 未来周期被拒绝或修正。
- 最终回答显示工具实际返回周期。

### 13.4 调用与去重

- 相同工具、对象和周期不重复调用。
- 合法翻页不被误拦截。
- 空结果后修改时间窗口可以重试。
- 达到最大轮次后仍使用已有证据完成回答。
- Mock 回归不要求固定工具数量，只验证所需证据和边界。

### 13.5 最终回答

- tools-off 综合不再调用工具。
- 综合失败时回退原始 draft。
- 选品回答覆盖结论、主要证据、驱动、风险/缺口和行动。
- 不出现工具结果未支持的具体数据和判断。
- 不出现当前任务无关的产品推广。

## 19. 已知问题：同义请求无法命中 FastMoss MCP 缓存

### 19.1 已验证现象

2026-08-01 两次使用相同预设 `fm-product-scout`、相同输入“解压玩具”：

- 旧会话 `1785566158648` 执行 5 个 FastMoss 工具。
- 新会话 `1785568278476` 执行 8 个 FastMoss 工具。
- 两轮间隔约 35 分钟，均未超过 TTL。
- 前后 13 个缓存文件仍共存于同一个 credential/URL scope，说明部署没有清空缓存，API Key 与 MCP URL 隔离域也没有变化。
- 13 个条目的 `hitCount` 均为 0。

当前缓存不按用户问题或 preset 命中，而按以下内容生成精确哈希：

```text
provider + credential/URL scope + tool endpoint + 完整 request
```

两轮实际参数没有一项完全相同：

- 类目搜索：旧轮只有 `query`，新轮显式增加 `top_k: 5`。
- 类目分析、类目排名和热销榜：旧轮使用 `week / 2026-W30`，新轮使用 `day / 2026-07-31`。
- 新品榜：类目字段和上新区间均发生变化。
- 新轮另增两次 `product_overview` 和一次 `product_video_list`。

其中类目搜索属于可避免的漏命中：两轮传给缓存层的 request 不同，但 FastMoss 最终执行参数都展开为 `top_k=5`、`max_total_results=15`，业务语义完全相同。缓存键在 MCP 默认值展开前生成，导致同义请求生成不同键。

### 19.2 当前边界

- FastMoss 聊天工具使用 Bridge 文件缓存，不使用 `data/api_cache.sqlite`。
- 宿主机持久化目录为 `data-dev/mcp_tool_cache_shared`，容器重建不会主动删除。
- 当前 FastMoss TTL 为 86,400 秒；延长 TTL 不能解决参数漂移导致的漏命中。
- 缓存应继续隔离不同 API Key、MCP URL、工具和真实业务窗口。
- 单日、整周、不同日期范围或不同商品不得因为自然语言问题相同而强行共用缓存。
- 当前不缓存整轮 LLM 回答，避免 Skill 版本、日期和上下文变化时复用陈旧结论。

### 19.3 后续修复方向

1. 在计算缓存键前形成“有效请求”：依据官方工具 schema 补齐或消除默认等价项。
2. 仅统一官方确认语义等价的参数，例如缺省 `top_k` 与显式默认 `top_k=5`。
3. 为选品 preset 稳定基础证据口径，例如最近完整日、明确的新品窗口和统一趋势窗口；模型仍可按证据需要追加深挖工具。
4. 不把固定基础口径扩展成固定调用剧本，也不让不同时间粒度错误共享数据。
5. 缓存元数据继续显示实际命中、TTL、age、endpoint，并增加可诊断的规范化后请求摘要或键前缀，禁止记录密钥。

### 19.4 验收用例

- 同一工具的参数对象键顺序不同仍命中。
- 缺省默认值与显式默认值命中同一条缓存。
- 相同 preset、市场、类目和日期口径重复请求时，基础工具稳定命中。
- `day` 与 `week`、不同日期范围、不同商品 ID 均不得串缓存。
- 4004 容器重建后仍能命中未过期条目。
- API Key 或 MCP URL 变化时使用新的隔离 scope。
- 错误和空异常响应不写入可复用缓存。
